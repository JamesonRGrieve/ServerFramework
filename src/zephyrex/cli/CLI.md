# Admin CLI (`zephyrex`)

One console script (`zephyrex`, also `python -m zephyrex`) for the server commands and the admin commands an agent or script runs on a server's CT to read or change data directly, like Frappe's `bench` or Nextcloud's `occ`.

## Layout

| File | Holds |
|---|---|
| `__init__.py` | `main(argv, *, app, stdin, stdout, stderr)`: builds the parser, dispatches server commands (`run`, `migrate`, `bootstrap`, `version`) as before, and admin commands through `Context.execute`. `_boot` boots the app for admin commands. |
| `Context.py` | `ExitCode`, `CLIError`, `Command`, `CommandGroup`, `CommandContext`, `global_options`, `execute`, dry runs, audit rows, shared-cache clearing, output. |
| `Records.py` | `models`, and `record list/get/create/update/delete`, in-process and over `--remote`. |
| `Admin.py` | The curated groups: `user`, `team`, `role`, `extension`, `cache`, and `seed`. |
| `Remote.py` | `RemoteClient`: REST calls with the root key. |
| `Extensions.py` | Mounts each loaded extension's `CLI_<Name>.py`. |

## Commands

- `models`: every loaded model with a manager, by wire name (`user_team`, `api_key`).
- `record list <model> [--filter F=V]… [--search JSON] [--fields] [--include] [--sort-by] [--sort-order] [--limit] [--offset] [--include-deleted]`. Soft-deleted rows are hidden unless `--include-deleted`; ROOT would otherwise see them.
- `record get <model> <id>`: `{record, etag}`.
- `record create <model> --data JSON|-`
- `record update <model> <id> --data JSON|- [--if-match ETAG]`: a stale ETag exits 4.
- `record delete <model> <id> [--if-match ETAG]`: soft delete; destructive.
- `user get <id|email>`; `user create --email E [--username] [--first-name] [--last-name] [--display-name] [--password-stdin]` (through ROOT-only `UserManager.create`, whatever `REGISTRATION_MODE` says); `user set-password <user>` (the password is stdin's first line, never argv); `user disable <user>` (sets `active=false` with `update_trusted` and revokes every session); `user enable <user>`.
- `team create --name N [--description] [--parent ID]`; `team members <team>`; `team add-member <team> <user> <role>` (the same as `role grant`); `team remove-member <team> <user>` (the same as `role revoke`; destructive).
- `role list [--team ID]` (system roles when no team is given); `role grant <team> <user> <role>` (adds the membership, or changes its role; a role is named by id, else by name, the team's own first, then a system role); `role revoke <team> <user>` (soft-deletes the membership; destructive).
- `extension list`; `extension info <name>`: the manifest, plus `loaded`.
- `cache clear [--model M]…` (destructive): clears the shared Valkey entity and response caches for those models' tables, or every model's.
- `migrate [up]` (upgrade core and extensions to head, then seed; `--dry-run` refused), `migrate status` (each component's heads against its current revisions), `migrate down --to TARGET` (destructive), `migrate revision <extension> -m MSG [--empty]` (writes the extension's next revision into its `migrations/versions`, autogenerated from its models against this database, so for a complete 001 point it at an empty one; honours `--extensions-path` for consumer extensions).
- `seed`: inserts every model's missing seed rows (`ModelRegistry._seed`). Admin boots skip seeding.
- `api-key create --name N [--user] [--team] [--role] [--expires-at]` (prints the raw key once), `api-key list [--user] [--include-revoked]`, `api-key revoke <id>` (destructive). These ship as the `auth_api_keys` extension's `CLI_ApiKeys.py` (`GROUP = "api-key"`).
- `<group> <command> …`: from extensions.

## Global options (before or after the command)

`--extensions CSV`, `--extensions-path PATH` (else `APP_EXTENSIONS` / `EXTENSIONS_PATH`), `--format json|table`, `--dry-run`, `--as USER`, `--reason TEXT`, `--yes`, `--remote URL`.

## Output and exit codes

stdout carries one JSON envelope: `{ok, command, dry_run, result | error, exit_code, …}`, plus `audited`, `caches_cleared` and `notes` after a real mutation, and `skipped_hooks` after a dry run. Logs go to stderr while a command runs (`lib.Logging.route_logs_to`), and move back afterwards. `--format table` prints rows or key/value lines instead.

| Code | Meaning | From |
|---|---|---|
| 0 | ok | |
| 1 | error | anything else |
| 2 | usage | bad arguments or JSON, destructive without `--yes`, an in-process-only option over `--remote` |
| 3 | not found | 404, unknown model, `--as` naming no single live user |
| 4 | conflict | 409, 412 (stale If-Match), 428 (If-Match required over REST) |
| 5 | permission | 401, 403 |
| 6 | validation | 400, 422, pydantic `ValidationError` |
| 7 | dry run refused | `--dry-run` with `--remote` |

## In-process execution

- **Boot:** `instance()` with `RUN_MIGRATIONS=false` and `SEED_DATA=false`, without uvicorn or the lifespan, so background services don't start and a read changes nothing.
- **Identity:** ROOT, or `--as <id|email>` (one live user) with that user's own permissions. Managers come from `CommandContext.manager(model)`, built for that requester, so hooks, validation, field ACLs and permission checks all run as they do for the API. Output is `manager._visible_payload` (the REST serialisation).
- **If-Match:** `--if-match` binds `lib.Preconditions.expect_versions(manager, {id: etag}, may_require=False)`. Without it the write isn't version-checked, since a direct manager call is unbound.
- **Destructive commands** run only with `--yes`, a typed `yes` at a terminal, or as a dry run.
- **Dry run** (mutating commands): `DatabaseManager.rollback_scope()` binds every sync session to one connection whose outer transaction is rolled back. A manager's `commit()` releases only a savepoint, so later reads in the command see its writes; on SQLite the scope emits `BEGIN` itself. While the scope is open, managers skip AFTER hooks (mail, uploads, webhooks don't roll back) and list them in `skipped_hooks`. The entity cache is unset for the run. A dry run writes no audit row and clears no cache. A side effect inside a manager method body itself (not a hook) still runs.
- **Audit:** with `meta_logging` loaded, every real mutation, successful or failed, writes an `AuditLog` row: `action=cli:<command>`, `user_id` = the requester, `resource_type/id` from `ctx.resource`, `additional_data {via: cli, as, reason, host, os_user, argv}`. In `argv`, each `--data` value is reduced to its keys. Every command also writes one structured log line (`cli {...}`).
- **Shared caches:** a server wires its Valkey entity and response caches in its lifespan, which the CLI doesn't run. So after a real mutation with `VALKEY_URI` set, the CLI clears both caches for every table it touched through `ctx.manager` (whole tables, since a changed index field leaves keys only the server knew).

## Remote execution (`--remote URL`)

The root key comes from `ZEPHYREX_ROOT_API_KEY` and is sent as `X-API-Key`. Requests go to `/v1/<model>` (or `--path`) with the body enveloped as `{<model>: …}` (or `--key`); a one-key response envelope is unwrapped. `list` filters only through `--search` (`POST …/search`). REST requires If-Match on update and delete unless `IF_MATCH_REQUIRED=false`. `--dry-run` (exit 7) and `--as` (exit 2) are in-process only.

## Extension commands

An extension's directory may hold `CLI_<Name>.py` defining `register(group: CommandGroup)`. Each `group.command(name, handler, help=…, mutates=…, destructive=…, remote=…)` returns an `argparse` parser for the command's own arguments. A handler is `(ctx: CommandContext, args) -> JSON-ready result`; a remote handler is `(client: RemoteClient, args)`. Commands mount as `zephyrex <group> <command>`, where the group is the module's `GROUP` (else the extension's name), only when the extension is in `--extensions`/`APP_EXTENSIONS`. A mutating handler names what it changed in `ctx.resource` and gets dry runs, audit and cache clearing from `execute`. A group named like a core command is refused.
